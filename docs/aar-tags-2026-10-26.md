## 3. Judgment: human in the loop
**Decisions the owner made:** build section 3 first; no test runs; nothing marked "proposed".
**Decisions the agent made alone, for owner review:**
- **What the model sees.** For a person: field values, tier, usual times, hours and whether remote is fine. Never the name, email or phone. For a task: title, description, when, location, effort, what to bring and the requirements as text. For a need: the title and how it repeats.
- **When tagging runs.** After the response, so adding a person or importing a file doesn't wait for the model. Tags appear on the next load of the screen. Imports go to the model 40 people at a time.
- **Limits.** Up to three tags per record, eight new tags per model call, and 200 tags per organization.
- **Names.** Two names that differ only in case or spacing are the same tag. Renaming to an existing name is refused and points to merge.
- **Colors.** A new tag takes the palette color used least so far. Merging keeps the color of the tag merged into.
- **The "new" mark** clears when a coordinator leaves the Settings page after seeing the Tags section, and when they rename a tag.
- **Where tags show.** On coordinator screens only. Volunteer screens are unchanged, by rule 2.
- **Who can change tags.** Admins and coordinators manage the set. A team lead can change the tags on a task they manage, but not on people or needs.
- **Open question 4** (tags on needs shared by partner organizations) stays open. A shared copy arrives in the partner's organization with no tags.

**Points where it should have escalated and didn't:** none known.

## 5. Consequence: what it cost or risked
**Observed:** every route answered as expected in the local walk-through, the screens rendered on a phone and a desktop with no page errors or sideways scrolling, and the merge moved both "kitchen help" records to "Kitchen".
**Risk:** a model that returns many tag names could grow the set quickly. The caps above limit it to eight new tags per call. Tagging sends record text to the model provider, so the rule in decision 0008 applies: the provider must not train on or keep prompts, and the owner records the provider before real data goes through.
**Downstream affected parties:** coordinators see new chips on four screens. Volunteers see nothing new.
**Expected failure if this run happened 100 times:** a few runs would pick chip colors that read poorly in dark mode on some screens, since only light mode was screenshotted.
